# 인증과 인가

## 책임 분리

**인증(Authentication)**은 요청자가 누구인지 확인한다. 로그인 자격 증명 또는 토큰을 검증하고, 신뢰할 수 있는 사용자 ID와 권한을 `Authentication` 및 `SecurityContext`로 전달한다. 인증 구성 요소에서 특정 신청서의 소유권이나 상태를 판단하지 않는다. 구조는 [Spring Security 인증 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/architecture.html)를 참고한다.

**인가(Authorization)**는 인증된 사용자가 해당 행위를 수행할 수 있는지 판단한다. 역할에 의한 기능 접근과 소유권·현재 상태에 의한 리소스 접근을 함께 검사한다. 인증 성공만으로 승인 권한이 생기지 않는다.

HTTP 보안 설정은 공개 경로와 인증 필요 경로를 구분한다. 서비스 진입점에서는 메서드 보안 또는 명시적인 인가 정책으로 역할을 확인하고, 트랜잭션 안에서 조회한 신청서의 소유권과 상태를 확인한 뒤 변경한다. 도메인 모델은 허용된 상태 전이를 보장한다. 메서드 보안의 활성화와 프록시를 통한 호출 조건은 [Spring Security 메서드 보안 문서](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html)를 확인한다.

## 역할별 권한

| 행위 | `DEVELOPER` | `DEVOPS_ADMIN` | `AUDITOR` |
| --- | --- | --- | --- |
| 신청서 생성 | 허용 | 별도 부여 시 허용 | 금지 |
| 신청서·결정 이력 조회 | 허용, 조회 범위 결정 필요 | 승인 업무 범위 | 감사 범위 |
| 신청서 수정·취소 | 본인 소유 + 대기 상태 | 관리자 역할만으로 부여하지 않음 | 금지 |
| 승인·반려 | 금지 | 허용 | 금지 |
| 카탈로그 조회 | 허용 | 허용 | 허용 |
| 카탈로그 생성·수정·삭제 | 금지 | 허용 | 금지 |

역할 간 상속은 요구사항으로 확정된 경우에만 부여한다. `DEVOPS_ADMIN`이라는 이유로 신청자의 편집 권한을 우회하지 않는다. `hasRole("DEVELOPER")`와 `hasAuthority("ROLE_DEVELOPER")`의 접두사 규칙을 일관되게 사용한다.

**미결정**: 개발자의 조회 범위는 본인 신청만인지 조직 전체인지 아직 정해지지 않았다. **초기 제안**은 개발자 본인 신청·이력, 관리자는 승인 대상 전체, 감사자는 감사 대상 전체다. 조회 기능을 구현할 때 확정하고 목록·상세·이력에 동일하게 적용한다.

## 리소스 인가

- 신청서 작성자 ID는 인증 정보에서 가져온다. 요청 본문의 작성자 ID나 처리자 ID를 권한 근거로 사용하지 않는다.
- 수정·취소는 역할만 검사하지 않고 `현재 사용자 ID == 신청자 ID`와 대기 상태를 함께 확인한다.
- 상세 조회와 이력 조회에도 조회 범위를 적용한다. 목록은 DB 조회 조건에 범위를 반영해 결과와 전체 건수가 함께 보호되게 한다.
- 회원가입의 기본 역할은 서버에서 `DEVELOPER`로 정하고, 관리자·감사자 역할 부여는 별도 권한이 있는 경로에서 처리한다.
- 감사자는 업무 데이터에 대한 모든 쓰기 경로에서 거부되어야 한다. 화면 버튼과 HTTP 메서드만으로 읽기 전용을 보장하지 않는다.

## 실패와 검증

인증 누락·실패는 `401`, 인증된 사용자의 권한 부족은 `403`으로 구분한다. 리소스 존재 은닉이 필요하면 타인 자원에 `404`를 반환하는 정책을 정하고 조회·변경에 일관되게 적용한다. 허용된 사용자가 잘못된 상태 전이를 요청하면 `409` 등 도메인 충돌 응답으로 구분한다.

실제 보안 필터 체인을 통과하는 요청으로 미인증, 만료/변조 토큰, 역할 부족을 검증한다. 리소스 인가는 소유자/비소유자와 대기/처리 완료 상태를 조합해 검증하고, 실패 시 DB 변경이 없는지 확인한다.
