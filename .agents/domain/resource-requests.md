# 도메인과 상태 머신

## 업무 객체

| 객체 | 책임과 데이터 |
| --- | --- |
| 자원 신청서 | 신청자, 인스턴스 타입/스펙, 목적, 예상 비용, 현재 상태를 보유한다. |
| 승인/반려 이력 | 대상 신청서, 처리자, 처리 시각, 이전/이후 상태, 결정 및 사유를 기록한다. |
| 자원 스펙 카탈로그 | 신청 가능한 인스턴스 타입과 스펙을 제공한다. |

신청자와 처리자는 인증된 사용자 식별자로 결정한다. 역할·소유권 판단은 [인가 규칙](../security/authentication-authorization.md)을 따른다.

**설계 제안**: 예상 비용은 `BigDecimal`로 표현하고 통화와 산정 기간을 명시한다. 신청 당시 스펙·비용을 스냅샷으로 보존하면 카탈로그 변경 후에도 과거 신청 내용을 재현할 수 있다. 적용 전에 비용 입력 주체와 산정 방식을 정한다.

**설계 제안**: 감사 목적의 승인/반려 이력은 추가·조회 중심으로 유지한다. 히스토리 CRUD가 필요하더라도 기존 결정의 수정·삭제와 정정 이력 추가를 구분한다. 참조 중인 카탈로그 항목은 비활성화하거나 삭제를 제한하는 정책을 먼저 정한다.

## 상태와 전이

목표 상태는 `PENDING`(대기), `APPROVED`(승인), `REJECTED`(반려), `EXPIRED`(만료)다. 신규 신청은 `PENDING`에서 시작한다.

| 현재 상태 | 행위 | 다음 상태 | 조건 |
| --- | --- | --- | --- |
| `PENDING` | 신청 내용 수정 | `PENDING` | 신청자 본인 |
| `PENDING` | 승인 | `APPROVED` | 승인 권한 보유 |
| `PENDING` | 반려 | `REJECTED` | 반려 권한 보유, 사유 검증 |
| `PENDING` | 만료 | `EXPIRED` | 만료 조건·실행 주체 결정 후 구현 |
| `PENDING` | 취소 | 취소 정책에 따라 결정 | 신청자 본인 |
| `APPROVED` / `REJECTED` / `EXPIRED` | 수정·취소·추가 결정 | 허용하지 않음 | 재신청·재심사는 별도 요구사항으로 정의 |

승인된 신청서는 수정 불가다. 승인·반려 등 상태 변경은 현재 상태를 확인하는 도메인 연산을 통해 수행하고, 상태 필드의 쓰기 경로를 제한한다. 실패한 전이에서는 신청서와 이력을 모두 변경하지 않는다.

## Kotlin 표현

- `enum class RequestStatus`: DB와 API에서 사용하는 유한한 상태 코드다. DB에는 문자열로 저장한다.
- `sealed class RequestState`: 상태별 데이터와 동작을 표현하는 도메인 모델로 사용한다. 예를 들어 반려 상태가 필요한 사유와 처리 정보를 보유하게 한다.
- 상태 머신은 현재 `RequestState`와 명령을 받아 다음 상태 또는 명시적인 전이 실패를 반환한다. `when`의 모든 분기를 처리해 상태 추가 시 누락을 컴파일 단계에서 찾는다.
- enum과 sealed 모델의 변환은 한 곳에서 관리한다. 두 값을 독립적으로 수정 가능한 상태로 보관하지 않고, 저장 데이터에서 도메인 상태를 복원한다.
- 시간에 따른 전이는 주입된 시계로 판단해 경계 시각을 재현할 수 있게 한다. sealed 계층 자체를 JPA 상속 매핑으로 연결할 필요는 없다.

상태 변경과 결정 이력 저장은 하나의 트랜잭션으로 처리한다. 동시 승인·반려·취소 경쟁은 버전 필드나 조건부 갱신 등으로 보호하고, 충돌 시 하나의 결정만 저장되도록 검증한다.

## 구현 전 결정할 정책

- **취소**: 기존 코드에는 `CANCELLED`가 있다. 이를 별도 상태로 유지할지, 별도의 취소 표식으로 표현할지 결정한다. 자발적 취소를 시간 만료인 `EXPIRED`로 치환하지 않는다. 상태 코드 변경 시 기존 데이터·API 호환성도 함께 다룬다.
- **만료**: 만료 기준 시각, 대상 상태, 실행 주체, 만료 이력 보존 방식을 결정한다. 위 표는 대기 신청의 만료를 초기 설계로 제시한다.
- **재처리**: 반려 후 재신청, 승인 취소, 관리자 본인 신청의 자가 승인 허용 여부는 추가 정책이 필요하다.

## 검증 기준

전이 표의 허용 행위와 비허용 행위를 각각 검증한다. 특히 비소유자 수정·취소, 승인 후 수정, 중복 승인, 반려 후 취소, 동시 결정에서 상태와 이력의 일관성을 확인한다.

sealed 계층과 완전한 `when` 분기의 언어 규칙은 [Kotlin 공식 문서](https://kotlinlang.org/docs/sealed-classes.html)를 참고한다.
