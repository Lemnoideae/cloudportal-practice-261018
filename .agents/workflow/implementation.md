# 구현과 완료 기준

## 작업 순서

1. **범위 확인**: 변경 대상 소스·빌드 설정과 관련 문서를 읽는다. 현재 구현과 목표 요구사항의 차이, 이번 작업에서 적용할 정책을 식별하면 완료다. 미결정 정책은 명시하고 영향받지 않는 작업을 계속한다.
2. **규칙 배치**: 입력 검증, 인증, 인가, 상태 전이, 저장의 책임을 배치한다. 각 규칙의 담당 경계와 실패 결과를 설명할 수 있으면 완료다.
3. **구현**: 요청 → 서비스 → 도메인 → 저장 → 응답의 한 업무 흐름을 연결한다. 해당 흐름에서 정책 우회와 불법 전이를 막고, 실패 시 부분 저장이 없으면 완료다.
4. **검증**: 변경된 업무 규칙의 성공·실패 경로에 적합한 검증을 실행한다. 실행 결과와 미실행 항목·이유가 확인되면 완료다. 기존 실패는 이번 변경으로 생긴 실패와 구분한다.
5. **기록**: 변경 동작, 학습 개념과 연결되는 설계 이유, 검증 결과를 보고한다. 정책 변경은 담당 문서에 반영하고 구현 상태의 중복 목록은 만들지 않는다.

## Java → Kotlin 전환 시

외부 API, DB 스키마, 권한, 상태 전이를 먼저 확인한다. 기존 동작 보존과 업무 규칙 수정은 변경 의도를 구분해 설명한다. null 계약, 생성자, 접근자, 프록시, Java 플랫폼 타입은 Kotlin 코드가 컴파일된 뒤에도 기존 호출·저장 경계에서 검증한다.

## 변경별 완료 증거

| 변경 | 필요한 증거 |
| --- | --- |
| 보안 | 인증 성공/실패, 역할별 허용/거부, 소유권과 조회 범위 |
| 상태 머신 | 허용/비허용 전이, 상태별 데이터 불변식, 결정 이력 원자성 |
| 영속성 | 저장 후 재조회, 제약 조건, 영향받는 동시 변경 동작 |
| DTO | 실제 바인딩과 검증 실패 응답, 정상 입력 처리 |
| 문서 | 상대 링크 유효성, 요구사항과 제안의 구분, 정책의 단일 원본 |

검증 명령과 의존 서비스는 현재 프로젝트 설정에서 확인한다. 코드 변경은 관련 컴파일·테스트를 실행하고, 문서만 바꾼 경우 링크·정합성 검증으로 완료할 수 있다.
